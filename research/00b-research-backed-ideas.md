# 00b · Research-backed ideas (beyond existing stacks)

Ideas for H-Stack drawn from 2025–2026 papers and engineering posts. "Not found in reviewed stacks" means not found in the cloned repos of superpowers, gstack, pstack (cursor/plugins), mattpocock/skills, addyosmani/agent-skills and ECC (grep over skills, hooks and docs, 2026-11-11); it does not mean nobody anywhere does it.

Verified 2026-11-11 against the primary sources (arXiv HTML full text, the engineering posts, the Claude Code docs). Section/table references are given so each number can be traced. The full verification log, with what changed and why, is in [00c](00c-beyond-every-stack.md#2-verification-log-for-00b). Where a paper has several versions, the version read is named.

## H-Stack original ideas

### A. Routing & intent
- **N1 Act / ask / stop router.** Every prompt is classified act, ask or stop (abstain). Questions are ranked by how much the answer would change the outcome; only the top 1–3 are asked. The intent check runs separately from the worker (Ask-or-Assume: separation gave +8.2 pp over a single agent prompted to check). *Partial precedent: gstack `plan-tune` tunes which questions fire; no reviewed stack has a separate act/ask/stop classifier.*
- **N2 Assumption ledger.** When proceeding without asking, assumptions are written to a visible list and each becomes a checkable item at the end.
- **N3 Explainable routing.** "Why that?" shows the classifier's reason; the user's correction is saved as a routing example.
- **N4 Suggest-don't-act proactivity.** Predicted next steps appear as offers, never actions (ProCodeBench: ≤ 35.6% intent prediction even for the best agent). Offer them at workflow boundaries (after a commit, after tests pass), not mid-task: in a 5-day field study, boundary suggestions got 52% engagement while mid-task ones were dismissed 62% of the time ([ProAIDE, arXiv 2601.10253](https://arxiv.org/abs/2601.10253)).
- **N5 Premise check (anti-sycophancy).** When the user states a cause or fact ("the bug is in X"), treat it as a hypothesis and verify it before building on it; say so respectfully when evidence disagrees. Prompting alone mitigates sycophancy poorly ([ELEPHANT, arXiv 2505.13995](https://arxiv.org/abs/2505.13995) §4.3), so the check must be an evidence step, not a tone instruction.

### B. Context engineering
- **N6 Minimal always-on context, A/B tested.** H-Stack's own always-on text is measured with vs without on a small task set (`claude plugin eval` runs the no-plugin baseline natively); anything that doesn't help is cut.
- **N7 Hook-maintained recitation.** A hook (not the agent) appends the current goal and step at the end of context after tool batches (`PostToolBatch`), so goals stay in the high-attention zone without spending agent turns on todo updates.
- **N8 Cache-aware injection.** All hook context is appended, stable, deterministically serialised; nothing rewrites earlier context or changes tool definitions mid-session. Cache reads cost 0.1× input; writes 1.25× (5-min) or 2× (1-hour) (Claude prompt-caching docs).
- **N9 Failure log that survives compaction.** "Tried X, failed because Y" is recorded and re-injected after compaction so the agent never retries a dead end.
- **N10 Restorable compression.** Handoffs keep paths, commands and IDs, not bulky content; anything dropped can be re-fetched.
- **N11 Context-rot guard.** With 1M-token windows and auto-compaction, running out is rare (Claude Code best practices); the risk is quality. Between unrelated tasks, suggest `/clear`; for long autonomous runs, hand off to a fresh session with a structured handoff. Lower priority than in older stacks.
- **N12 Hybrid code navigation.** Code graph for structural questions (callers, hubs, impact), grep/read for everything else (graph alone loses quality: 0.83 vs 0.92).

### C. Verification
- **N13 Read-only tests while implementing.** A guard blocks edits to test files outside the "write tests" step; any test change is shown to the user as a diff. Removes the Claude-typical cheat (test edits, >79% of Claude cheating) but not special-casing, so N14 is still needed.
- **N14 Test-tamper scanner.** Flags weakened assertions, skips, raised timeouts, special-cased inputs, call-count state, monkey-patched clocks, `__eq__` overloads (the four ImpossibleBench cheat types).
- **N15 Contradiction stop.** If tests contradict the spec, stop and explain instead of making them pass, with a real stop path (ImpossibleBench abort flag: GPT-5 54% → 9%).
- **N16 External-signal-only retries.** Every retry must cite a new external signal (test output, error, measurement, user input); no blind "reflect and fix".
- **N17 Counterfactual fix check.** Revert the fix → the new test must fail; reapply → it passes. Proves the test actually covers the bug.
- **N18 Diff-targeted mutation check.** Mutate only the changed lines a few ways; new tests must catch the mutants, else they're flagged as weak.
- **N19 Blind cross-review.** Reviewer gets only the diff + spec, fresh context, no author reasoning; grades binary rubric items; uses a different model family when available. *Cross-family review already exists in gstack (`codex`, autoplan `MODEL_FAMILY_CONFLICT`) and pstack (`show-me-your-work`); H-Stack's addition is the rubric format and disagreement filter from 2604.06996.*
- **N20 Risk-gated tournament.** Only for high-risk changes: 2–4 approaches in worktrees, rubric-based scoring picks the winner. Branch only at uncertain steps: EGSS ([arXiv 2602.05242](https://arxiv.org/abs/2602.05242)) uses tool-selection entropy (+5–10% on SWE-bench Verified, −28% tokens vs other test-time scaling); entropy isn't exposed in Claude Code, so H-Stack uses disagreement between two cheap plans as the proxy. *pstack `arena` already runs parallel candidates.*
- **N21 Disagreement as the uncertainty signal.** Escalate verification when independent checks disagree (two reviewers, test vs reviewer), not on self-reported confidence.

### D. Security
- **N22 Dependency gate.** Before any install, manifest edit **or new import**: package exists, isn't brand new, has real usage history, isn't a near-miss of a popular name; otherwise ask. Most hallucinated names are not near-misses (only 13.4% within edit distance 2), so age/usage matters more than typo distance; a hijacked agent can add an import and let the user install it (Beurer-Kellner et al., §4.10). *addyosmani and ECC mention typosquats in checklists; none ships an automatic pre-install check.*
- **N23 Untrusted-content quarantine (CaMeL-lite).** Web pages, issues, PR comments and fetched docs are tagged untrusted; a tool-less subagent turns them into strictly formatted output (e.g. an API description or a fixed schema) before the main agent sees it; while untrusted content is in play, irreversible actions need a confirm. A tool-less summariser alone protects control flow but not data flow: injected text can still change the arguments of a later tool call (CaMeL §2), so values derived from untrusted content are tracked into tool arguments. Auto mode already blocks "actions that look driven by content Claude read rather than by you", so H-Stack adds provenance, not a second classifier.
- **N24 Skill and hook supply-chain scan.** Any third-party skill/hook/MCP config is scanned for injection, exfiltration and odd shell before it's enabled; MCP tool *descriptions* are scanned too (tool poisoning hits up to 72.8% success, Claude 3.7 Sonnet refused < 3%; [MCPTox, arXiv 2508.14925](https://arxiv.org/abs/2508.14925)).

### E. Memory & learning
- **N25 Episodic-first memory.** Raw episodes (task, what was tried, outcome, evidence) are the primary record; consolidation into rules is gated, proposed, and human-approved. Agents follow raw trajectories but often ignore or misread condensed lessons ([Not Always Faithful Self-Evolvers, arXiv 2601.22436](https://arxiv.org/abs/2601.22436)).
- **N26 Delta lessons with provenance.** Lessons are added or refined one item at a time, each linked to the episode that produced it, with a date, helpful/harmful counters (ACE §3.1) and a re-check; lessons that stop holding are pruned. No in-place rewriting (2605.12978 Table 5). *gstack's learnings log is append-only (latest entry per key); the episode link and counters are H-Stack's addition.*
- **N27 Learn from user edits.** Compare what Claude wrote with what the user committed afterwards; infer a readable preference **for that kind of context**; retrieve it for similar contexts and propose it as a rule only when it holds across contexts (CIPHER: context-agnostic preferences did worse than no learning).
- **N28 Curated skills only.** Claude may *draft* a skill, but it ships only after passing its eval and user approval (self-generated skills: −8.1 to −11.5 pp vs no skills in SkillsBench v4).
- **N29 Skill gym (reflective tuning).** Offline: replay real trajectories, let a reflector propose skill-text edits, keep only edits that improve the eval set without regressions (GEPA-style Pareto).
- **N30 Sleep-time prep.** While idle or nightly via scheduled tasks: refresh repo map/glossary, triage flaky tests, audit dependencies, pre-answer likely next questions for the open task. Only where many later queries share the context (sleep-time gains depend on predictability).

### F. Human factors
- **N31 Review guide with every change.** What changed, risk per hunk, where to look first, what was verified and how. Optimises the reviewer's minutes (only 48% of developers always check AI code).
- **N32 Question budget.** Non-blocking questions are batched to the end; blocking ones are capped per task.
- **N33 Change-size governor.** Keeps diffs reviewable; splits large work into stacked steps automatically.

### G. Autonomy & orchestration
- **N34 Native-first.** Use `/goal` for completion conditions, cloud scheduled tasks for scheduled work, dynamic workflows/agent view for fan-out, auto mode for permissions; H-Stack supplies the conditions and checks, not another loop engine. Note: the `/goal` evaluator reads only the transcript and runs nothing itself, so goal conditions must name evidence a hook puts in the transcript (see N100 in 00c).
- **N35 Long-run protocol.** Initializer writes a feature list (JSON, all `passes: false`) + progress file + `init.sh`; each session/iteration smoke-tests, does one item, verifies end-to-end, updates both.
- **N36 Effort-scaling rules.** Explicit budgets by task size. Anthropic's research system used: simple fact-finding = 1 agent, 3–10 tool calls; comparisons = 2–4 subagents, 10–15 calls each; complex research = 10+ subagents. For coding, H-Stack defaults lower because coding has fewer truly parallel parts: direct = 0 subagents; light = ≤ 1; full = 2–5 with a lead; tournament only when risk is high.
- **N37 Delegation brief standard.** Every subagent brief: objective, scope boundary, output format, tools, what's already known, done-criteria.
- **N38 Failure-signature monitor.** Detects MAST-style failures live: repeated identical tool calls (the most common mode, 15.7%), premature "done", ignoring a subagent's result, unverified completion; intervenes with a factual note.

### H. Cost
- **N39 Model routing by step.** Triage/classification on a small model; architecture, debugging and review on the strongest; per-step via mods `agent.spawn` (choose a subagent's model), skill `model`, or subagent `model: haiku`.
- **N40 Code-mode for bulk tool work.** When many tool calls are needed, write a script that calls them instead of looping through tool calls.

### I. Keeping H-Stack itself honest
- **N41 No unproven skills.** Each skill ships with an eval; it must beat the no-skill baseline or it's removed. `claude plugin eval` (Claude Code v2.1.269+) runs each case with and without the plugin and reports Δ natively.
- **N42 Retire skills the model has outgrown.** Re-run evals on each new model release; a skill the base model now passes without is retired ("every component in a harness encodes an assumption about what the model can't do on its own", Anthropic harness-design post).
- **N43 Activation telemetry (local).** Which skill was picked, used, and whether the user corrected course; feeds N3 and N29. `/skill-doctor` already reports each skill's context cost and use count; H-Stack adds the correction signal.
- **N44 Invest where skills help most.** SkillsBench gains are largest where procedure is under-represented in pretraining (natural science +28.8 pp, cybersecurity +18.9) and smaller for software engineering (+11.6); H-Stack skills encode project- and domain-specific procedure, not general best practice.

### J. From Cloudflare's security work ([deep dive](09-security.md#cloudflare-deep-dive))
- **N45 Light by default, heavy on request.** Every heavy skill has a guidance mode (answer, no files, no fan-out) and a full mode that runs only when explicitly asked; ambiguous → one question.
- **N46 Three-verdict findings everywhere.** Reviews, audits and investigations report `confirmed` / `needs_validation` (with the exact missing fact) / `rejected`. Only confirmed items get a severity.
- **N47 Claim schema + deterministic validator.** Structured outputs (findings, review results, plans) are checked by plain code: cited files exist, lines match, patches parse, tests run. The model never grades its own format.
- **N48 Coverage ledger.** Reviews and audits track what was checked (area × concern) and what wasn't; "not covered" is said out loud; later runs fill gaps and re-check changed code instead of re-reading everything.
- **N49 Reserve verification budget first.** Before spending on exploration, reserve the tokens/agents needed to verify what will be found.
- **N50 Wishlist instead of guessing.** When blocked on something only the user can provide (credentials, a config, a running service), Claude files a short request and parks the task; it resumes when supplied. Replaces both guessing and giving up.
- **N51 Shallow-result detector.** A review/hunt/investigation that finds nothing is flagged as possibly shallow and re-run with a different angle, not reported as "all clear".
- **N52 Evidence-driven tooling.** Log which tools agents actually call; don't add tools or MCP servers until usage shows a need (Cloudflare's agents never called Semgrep).
- **N53 Error-as-success guard.** Treat API/tool errors that arrive as normal text as failures; never count an empty result after an error as success.
- **N54 Execution sandbox for untrusted code.** Running target code from untrusted sources (PRs, dependencies, downloaded repos) happens with no network, allowlisted env, read-only source, resource limits.
